# REQ-001: event spec for review

> We're adding a **Buy now** button on product pages that skips the cart and goes straight to checkout. Need tracking so we can see if it helps. Ship date Dec 9.

**Summary.** Track the new Buy now button on product pages (PDP) and attribute checkouts and orders to it, so the Buy now path can be compared with the cart path. There are three changes. (1) A new buy_now_clicked event fires on the PDP. It is deliberately not a new source value on product_added_to_cart, because Buy now skips the cart and counting it as an add would inflate add_to_cart_rate. (2) checkout_started is extended with an optional checkout_source property. (3) order_completed is extended with the same optional checkout_source property. With these, the funnel product_viewed → buy_now_clicked → checkout_started(buy_now) → order_completed(buy_now) can be compared with product_viewed → product_added_to_cart → checkout_started(cart) → order_completed(cart). Target ship date is Dec 9.

## Questions for the PM
- Does Buy now create a cart (even a temporary single-item one) with a cart_id? checkout_started requires cart_id, so if there is no cart we need to agree on what ID to send. Otherwise Buy now checkouts can't be logged and checkout_conversion would be skewed.
- What does 'helps' mean for this launch? For example: more orders per product view, higher checkout_conversion, or faster time to purchase. Will it launch as an A/B test or to everyone? If it's a test, we should add the experiment/variant assignment so exposure can be measured.
- Is Buy now on web only (/p/*) or also in the iOS/Android apps? Does the Buy now checkout offer store pickup, or ship only?

## Events

| Event | Change | Fires when |
|---|---|---|
| `buy_now_clicked` | new | Fires when a user taps/clicks the Buy now button on a product page and the click is accepted, i.e. required options such as size are selected and navigation to checkout begins. Fires once per accepted click. It does not fire when the click is blocked by validation. |
| `checkout_started` | extend | Unchanged: fires when checkout begins. It now also fires when checkout is reached via Buy now, with checkout_source = buy_now. |
| `order_completed` | extend | Unchanged: fires when an order is successfully placed. |

**buy_now_clicked**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `product_id` | string | yes | any |
| `quantity` | integer | yes | any |
| `price` | number | no | any |

**checkout_started**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `checkout_source` | string | no | cart, buy_now |

**order_completed**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `checkout_source` | string | no | cart, buy_now |

## KPIs to confirm before engineering starts

- [ ] **add_to_cart_rate** (owner: growth): Buy now is a cart-skipping path on /p/*. Users who would have added to cart may use Buy now instead, so add_to_cart_rate can drop even if purchases rise. Buy now is intentionally not logged as product_added_to_cart, so growth should confirm they want it excluded from this KPI. They may also want a companion 'PDP purchase intent' metric that adds buy_now_clicked.
- [ ] **checkout_conversion** (owner: finance-analytics): Buy now adds a new stream of checkout_started and order_completed events with a different (likely higher-intent) conversion profile, which shifts the daily blended rate. If Buy now checkouts fail to fire checkout_started (e.g. no cart_id), orders would rise without matching starts and the KPI would be inflated. The new checkout_source property lets finance-analytics split the rate by path.
- [ ] **store_pickup_adoption** (owner: retail-ops): If the Buy now checkout defaults to or only offers shipping, the extra Buy now orders would lower the pickup share of order_completed.
- [ ] **return_rate** (owner: ops-analytics): Buy now may change order volume (the denominator) and could bring more impulse purchases that are returned more often, so return_rate may move over the 60-day window. checkout_source on order_completed allows the rate to be split by path.

- `stg_checkout_started`: 6 valid samples pass; 2/2 broken samples caught

**Privacy.** No personal data is needed. Buy now often prefills saved address/payment or uses express wallets (Apple Pay/Google Pay). Do not attach email, name, phone, shipping/billing address or any payment details to buy_now_clicked, checkout_started or order_completed. Identify users only through the existing anonymous/user ID handled by the analytics SDK. If the Buy now redirect URL carries query parameters (e.g. prefilled contact info or tokens), make sure they are not captured in page_viewed.page_path or referrer; strip query strings or allowlist parameters.
