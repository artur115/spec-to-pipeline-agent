# REQ-002: event spec for review

> hey can we track when people add stuff to cart from their wishlist page? want to compare vs PDP adds

**Summary.** Jon wants to compare add-to-cart from the wishlist page against add-to-cart from the PDP. The catalog already has product_added_to_cart, with a `source` property whose enum is pdp, search and recommendation. So we don't need a new event: we extend `source` with a new allowed value, 'wishlist'. Jon can then compare source = 'wishlist' against source = 'pdp'. If he wants adds per wishlist visit rather than raw counts, the existing page_viewed event on the wishlist path can serve as the denominator without changes.

## Questions for the PM
- Does the wishlist page fire product_added_to_cart today, and if so, what `source` does it send (none, or 'pdp')? This decides whether add_to_cart_rate gains new events or only gets re-attributed, and how to read historical data.
- If the wishlist has an 'Add all to cart' button, should it fire one product_added_to_cart per product (recommended, consistent with the catalog) or a single event?
- Should add_to_cart_rate (owned by growth, scoped to /p/*) count wishlist adds, or be filtered to source = 'pdp'?

## Events

| Event | Change | Fires when |
|---|---|---|
| `product_added_to_cart` | extend | Fires when a user adds an item to the cart from the wishlist page (web wishlist page and app wishlist screen) and the cart add succeeds. Use the same success condition as the existing PDP add. Send source = 'wishlist'. Fire one event per product added; `quantity` is the number of units added. |
| `page_viewed` | reuse | Existing behavior. Fires on wishlist page load with the wishlist page_path (e.g. /wishlist). No change needed. |

**product_added_to_cart**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `source` | string | no | pdp, search, recommendation, wishlist |

## KPIs to confirm before engineering starts

- [ ] **add_to_cart_rate** (owner: growth): This KPI is built on product_added_to_cart. If wishlist adds aren't tracked today, they will start firing; any wishlist add in a session that also has a product view could then be counted, raising the rate. If they are tracked today under another or missing source, the counts stay the same but the attribution shifts to 'wishlist'. Growth should confirm whether the KPI should filter to source = 'pdp' (it is scoped to /p/*).
- [ ] **newsletter_signup_rate** (owner: growth): (added by the config check) built on page_viewed, which this spec reuses

**Privacy.** No personal data is needed. Send only product_id, quantity and source. Do not attach wishlist owner details (name, email), a shared-wishlist URL or slug, or any wishlist identifier derived from the user's email or name. If page_viewed is used for the wishlist page, make sure page_path and referrer carry only the path, with no user identifiers or share tokens in path segments or query strings; strip query parameters if shared wishlist links include them.
