# REQ-004: event spec for review

> Launching curbside pickup as a third option at checkout next to ship and in-store pickup. Retail ops needs it in their pickup numbers.

**Summary.** Extend the existing order_completed event; no new event is needed. Curbside orders keep fulfillment_method = 'pickup', which leaves the field's type and allowed values unchanged. A new optional property, pickup_type ('in_store' | 'curbside'), records which kind of pickup the customer chose. This means retail ops' store_pickup_adoption KPI counts curbside orders automatically, with no change to its definition, and the two pickup kinds can still be reported separately. Implementation rules:
- Send pickup_type only when fulfillment_method = 'pickup'. Omit it for 'ship'.
- Older app versions will send 'pickup' with no pickup_type. Treat those as in_store, since curbside did not exist before this launch.
- Deploy the schema update before the client change ships. order_completed has additionalProperties: false, so events carrying pickup_type would otherwise be rejected.

Alternative if retail ops prefers it: add 'curbside' as a third value of fulfillment_method instead. That requires changing the store_pickup_adoption definition to pickup OR curbside, and any existing query that filters on 'pickup' would silently miss curbside orders. This spec avoids that risk.

## Questions for the PM
- Should store_pickup_adoption count curbside and in-store pickup together (this spec's default, since curbside is sent as fulfillment_method = 'pickup'), or does retail ops want curbside as a separate number or breakdown in the KPI definition?
- Does retail ops need pickup numbers by store? If so, we would add an optional store_id (internal store identifier) to order_completed; it is not included in this spec.
- Is curbside launching on web checkout, the iOS/Android apps, or all of them? This determines which clients must send pickup_type and from which release.

## Events

| Event | Change | Fires when |
|---|---|---|
| `order_completed` | extend | Unchanged: fires once when an order is successfully placed (order confirmation). The new property is set from the fulfillment option the customer selected at checkout. |

**order_completed**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `pickup_type` | string | no | in_store, curbside |

## KPIs to confirm before engineering starts

- [ ] **store_pickup_adoption** (owner: retail-ops): Curbside orders are sent as fulfillment_method = 'pickup', so they join this KPI's numerator from launch and the pickup share will rise. That matches the request to include curbside in pickup numbers. If retail ops wants in-store only, the definition needs an added filter: pickup_type is 'in_store' or missing.
- [ ] **checkout_conversion** (owner: finance-analytics): This KPI uses order_completed as its numerator. The intended counts don't change, but if clients send pickup_type before the schema is updated, those events fail validation (additionalProperties: false). Every pickup order, in-store and curbside, would then drop out of orders and push conversion down. The schema must be deployed first.
- [ ] **return_rate** (owner: ops-analytics): This KPI uses order_completed as its denominator. The same deploy-order risk applies: rejected pickup orders would shrink completed orders and inflate the return rate. The KPI's definition and numbers are otherwise unaffected. Returns can now also be broken down by pickup_type.

**Privacy.** Curbside flows usually collect personal data for arrival notifications, such as phone number, customer name, vehicle make, model or colour, licence plate, and sometimes location or ETA. None of these may be added to order_completed or any analytics event. pickup_type carries only the enum value. If a store breakdown is needed, use an internal store_id, never a store address or the customer's address. If arrival or handoff events are wanted later, key them on order_id only and keep contact and vehicle details in the operational system, not in analytics.
