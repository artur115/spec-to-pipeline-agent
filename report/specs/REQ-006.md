# REQ-006: event spec for review

> Search now has filters (category, price range, in-stock only). Track which filters people use and whether filtered searches lead to clicks.

**Summary.** Track search filter usage and whether filtered searches lead to result clicks. This builds on the existing search events and does not redefine searches. (1) A new event, search_filter_applied, fires each time a user changes a filter on the results page. It answers 'which filters do people use'. (2) search_performed and search_result_clicked are extended with optional filter-state properties and a client-generated search_id. A click can then be attributed to a filtered or unfiltered result set, and to the specific filters active at click time. Changing a filter must NOT fire another search_performed. If it did, the search_success_rate denominator would inflate. The filter change is captured only by search_filter_applied.

## Questions for the PM
- Is the price range a set of preset buckets (e.g. 'under $50', '$50–$100') or a free min/max slider? If buckets, I'd swap filter_price_min/max for an enum of bucket ids.
- Can users select more than one category at once? The spec uses an array to cover both cases, but confirm so engineering can validate it.
- Do you also need filter removals and 'clear all' tracked, or only filters being applied? This spec includes a filter_action of applied/removed/cleared; drop it if removals don't matter.
- Are the filters live in the iOS/Android apps as well as web, or web only? Older app versions won't send the new optional properties, so filtered-vs-unfiltered comparisons should be limited to versions that do.

## Events

| Event | Change | Fires when |
|---|---|---|
| `search_filter_applied` | new | Fires once when the user changes a search filter on the search results page (category, price range, or in-stock toggle) and the updated result set has loaded. It fires on apply, remove, and clear-all. It does not fire on initial page load when filters are pre-set from the URL; that state is captured on search_performed instead. |
| `search_performed` | extend | Unchanged: fires when the user submits a search query. It must NOT fire again when only filters change. |
| `search_result_clicked` | extend | Unchanged: fires when the user clicks a search result. |

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `search_id` | string | yes | any |
| `filter_type` | string | yes | category, price_range, in_stock_only, all |

| `filter_categories` | array | no | any |

| `filter_in_stock_only` | boolean | no | any |

## KPIs to confirm before engineering starts

- [ ] **search_success_rate** (owner: growth): Both of its events (search_performed, search_result_clicked) gain new properties. The definition is unchanged if filter changes do not fire search_performed. If engineering instead fires search_performed on each filter change, the denominator inflates and the rate drops. Growth may also want to segment the KPI by is_filtered once data accrues; filtered and unfiltered numbers will only be complete for app versions that send the new properties.

**Privacy.** Filter values are product attributes, not personal data, so the new properties carry no PII. Send category filters as internal category slugs, not display text. The new search_filter_applied event deliberately uses search_id instead of repeating the free-text query. This avoids copying user-typed text, which could contain names, emails or phone numbers, into another event. The existing query property on search_performed and search_result_clicked has that risk today. Consider scrubbing email- and phone-like patterns client-side before sending. search_id must be a random UUID per query and must not be derived from any user or device identifier.
