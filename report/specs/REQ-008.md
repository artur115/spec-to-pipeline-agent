# REQ-008: event spec for review

> Returns flow gets a required reason dropdown: too small, too big, damaged, not as described, changed mind. Ops wants return reasons in reporting.

**Summary.** Extend the existing return_requested event with an optional return_reason property. Its allowed values match the five dropdown options: too_small, too_big, damaged, not_as_described and changed_mind. No new event is needed, because return_requested already fires per order_id + product_id. That means a reason can be attached to each returned item, and Ops can report return reasons by SKU, by category (via product_id) and over time. The property is optional in the schema because older app versions won't send it, even though the dropdown is required in the UI. The event's trigger point must not change.

## Questions for the PM
- Is the reason chosen once per return request or separately for each item? return_requested fires once per product_id, so if one reason covers a multi-item return, engineering should copy that reason onto each item's event.
- Will the dropdown ever include an 'Other' option or a free-text comment box? If so, add only an 'other' enum value and do not send the free text to analytics.
- Does the new dropdown ship on web and the iOS/Android apps at the same time? If not, Ops reporting will show null reasons from platforms that haven't shipped yet, and these should be shown as 'unknown' rather than dropped.

## Events

| Event | Change | Fires when |
|---|---|---|
| `return_requested` | extend | Unchanged: fires once per returned item when the customer submits a return request in the returns flow (/returns). The selected dropdown value is sent with the event. The firing point must not move, for example to a separate reason-selection step. |

**return_requested**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `return_reason` | string | no | too_small, too_big, damaged, not_as_described, changed_mind |

## KPIs to confirm before engineering starts

- [ ] **return_rate** (owner: ops-analytics): return_rate counts return_requested events against order_completed. Adding an optional property doesn't change the event count, provided the trigger stays the same. However, making the reason a required field adds friction to the returns flow and could lower submitted returns, which would move this KPI. The same happens if the event is accidentally moved or double-fired during the change. ops-analytics should confirm the trigger is unchanged and watch for a step change in return_rate after launch.

## Pipeline proof

- `stg_return_requested`: 6 valid samples pass; 3/3 broken samples caught

**Privacy.** return_reason is a closed enum, so it carries no personal data. Do not add a free-text comment or 'please explain' field to this event, because customers often write names, addresses or phone numbers in such fields. If a comment box is added later, keep the text in the returns system only and, at most, send a boolean such as has_comment. Do not add the customer's email, name, shipping address or RMA/label details to the event. order_id and product_id are enough to join to operational systems if needed.
