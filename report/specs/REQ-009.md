# REQ-009: event spec for review

> Track opens of push notifications in the app (iOS + Android), with which campaign the push came from.

**Summary.** Extend the existing app_opened event rather than adding a new one. A push-notification open is an app open whose source is a push tap. Two optional properties are added: open_source, which says how the app was opened, and push_campaign_id, which carries the campaign identifier from the push payload. The existing platform property already covers iOS and Android. No new event is needed for app launches or foregrounds that come from a push tap. Taps on a push while the app is already in the foreground would not be captured; see the first clarifying question.

## Questions for the PM
- Do you need to count taps on a push that arrive while the app is already open and in the foreground? These do not open the app, so they would not fire app_opened. Firing app_opened for them would inflate app_retention_d7. If you need them, we would add a separate push_notification_opened event for that case only.
- Where should the campaign identifier come from? Is there a stable campaign ID field in the push payload from our push provider (e.g., Braze or OneSignal), set the same way on iOS and Android? Or should we use the campaign name, which risks free text?
- Do you also want other open sources (e.g., deep link or email link) distinguished now? Or is direct vs. push_notification enough for this request?

## Events

| Event | Change | Fires when |
|---|---|---|
| `app_opened` | extend | Unchanged: fires when the app is launched (cold start) or brought to the foreground, on iOS and Android. If that launch or foreground was caused by the user tapping a push notification, the client sets open_source = push_notification and push_campaign_id from the notification payload. Otherwise it sets open_source = direct. Do not fire an extra app_opened for push taps that happen while the app is already in the foreground. |

**app_opened**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `open_source` | string | no | direct, push_notification |
| `push_campaign_id` | string | no | any |

## KPIs to confirm before engineering starts

- [ ] **app_retention_d7** (owner: mobile): This KPI is built on app_opened. The new properties alone don't change the counts. However, the push-open code path could change how many app_opened events fire: firing it on foreground push taps would add events, and fixing push launches that currently skip app_opened would also add events. Either would shift D7 retention. Confirm with mobile that the firing rules stay exactly the same.

## Pipeline proof

- `stg_app_opened`: 6 valid samples pass; 3/3 broken samples caught

**Privacy.** Send only a campaign identifier (an ID or slug) from the push payload. Do not send the notification title, body or personalization fields, which can contain the user's name or order details. Do not send the device push token or any provider user ID. If the provider only exposes a campaign name, check that names never include customer data before using them as push_campaign_id.
