# REQ-012: event spec for review

> New size guide modal on footwear and apparel product pages. We think it reduces fit returns. Track opens.

**Summary.** Track opens of the new size guide modal on footwear and apparel product pages, and make fit returns measurable so the hypothesis can be tested. guide_viewed is not reused: it means trail guide views, and reusing it would distort trail_guide_engagement. Add a new event, size_guide_opened, keyed on product_id. The analysis path is size_guide_opened, then product_added_to_cart, then order_completed, then return_requested, joined on product_id and user/session. return_requested has no reason today, so fit returns cannot be told apart from other returns. This spec adds an optional return_reason to return_requested. If the PM or ops-analytics already gets return reasons from another source (for example the OMS or returns platform), drop that extend. Implementation requirements: (1) Fire size_guide_opened once per modal open, not on re-render or tab switches inside the modal. (2) Opening the modal must not fire page_viewed or product_viewed, even if it changes the URL, hash or route.

## Questions for the PM
- Does the returns flow (or the returns/OMS system) already collect a return reason? If it does, which options does the customer choose from? The return_reason values should match those options exactly. If the data already exists outside the event stream, we can drop the return_requested extend.
- Where can the modal be opened from (for example a link next to the size selector, a prompt after a size error, or elsewhere)? Do you want to compare these entry points? If so, we'll add an optional entry_point property with fixed values.
- Does the size guide include a fit finder or calculator (foot length, height, etc.)? If it does, do you want to track that a recommendation was made? We would record only a completion flag and never the measurements.

## Events

| Event | Change | Fires when |
|---|---|---|
| `size_guide_opened` | new | Fires on the client when the size guide modal finishes opening on a product detail page (/p/*). Fires once per open. Does not fire on re-renders, on tab or unit switches inside the modal, or on close. |
| `return_requested` | extend | Unchanged: fires when a return is requested for an order line. |

**size_guide_opened**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `product_id` | string | yes | any |
| `category` | string | yes | footwear, apparel |

**return_requested**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `return_reason` | string | no | too_small, too_large, fit_other, not_as_described, damaged_or_defective, changed_mind, other |

## KPIs to confirm before engineering starts

- [ ] **return_rate** (owner: ops-analytics): This spec changes return_requested, which is one of this KPI's two events. The new property is optional and the firing logic must not change, so the KPI's numbers should not move. ops-analytics should confirm the change and do QA on return counts after release. The size guide is also expected to lower return_rate. That is a product effect, not a tracking change.
- [ ] **add_to_cart_rate** (owner: growth): The modal lives on /p/* pages. If it is built as a route or URL change that fires product_viewed again, it would inflate the denominator. The spec says the modal must not fire product_viewed. The size guide may also really affect add-to-cart, which is a product effect.
- [ ] **newsletter_signup_rate** (owner: growth): page_viewed is part of this KPI's inputs. If opening the modal fired page_viewed through a URL or hash change, page and session counts could move. The spec says the modal must not fire page_viewed.

## Pipeline proof

- `stg_size_guide_opened`: 6 valid samples pass; 3/3 broken samples caught
- `stg_return_requested`: 6 valid samples pass; 3/3 broken samples caught

**Privacy.** size_guide_opened carries only product_id and category. Do not capture any personal data (name, email, phone, address). If the modal has a fit calculator, do not send body measurements (foot length, height, weight, chest, etc.) or the computed size tied to the user. Those inputs stay on the client. For return_reason, send only the enum code the customer selected. Never send free-text return comments, because customers often put names, addresses or contact details there.
