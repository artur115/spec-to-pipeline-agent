# REQ-014: event spec for review

> Out-of-stock products get a 'Notify me when back in stock' button that takes an email. Track sign-ups per product.

**Summary.** Add one new event, back_in_stock_alert_requested. It fires when a shopper successfully signs up for a 'Notify me when back in stock' alert on an out-of-stock product. It is keyed by product_id (SKU), so sign-ups can be counted per product. The email address is never sent to analytics. No catalog event covers this action. newsletter_signed_up is also an email sign-up, but it is for marketing-list subscriptions. Adding a 'back_in_stock' value to its signup_location would inflate newsletter_signup_rate, so a separate event is the safer choice. No existing events need to change.

## Questions for the PM
- Does submitting the back-in-stock form also subscribe the shopper to the marketing newsletter? If it does, should newsletter_signed_up fire as well? That would change newsletter_signup_rate.
- Do you only need a count of sign-ups per product, or a rate (sign-ups per out-of-stock product view)? A rate would need an optional in_stock boolean added to product_viewed. That would be a separate extend.
- Is the button on web product pages only (/p/*), or also in the iOS/Android app?

## Events

| Event | Change | Fires when |
|---|---|---|
| `back_in_stock_alert_requested` | new | Fires once when the back-in-stock form on an out-of-stock product is submitted and the backend confirms the alert was created. It does not fire on button click, on opening the form, or on failed or invalid submissions. If the same shopper signs up again for the same product, fire it only if the backend creates a new alert. |

**back_in_stock_alert_requested**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `product_id` | string | yes | any |
| `category` | string | no | any |
| `price` | number | no | any |

## KPIs to confirm before engineering starts

- [ ] **newsletter_signup_rate** (owner: growth): This KPI should not change, because the back-in-stock sign-up is a separate event and must not fire newsletter_signed_up. Confirm this with growth. If the form also opts shoppers into the newsletter, or if engineering reuses newsletter_signed_up for it, newsletter sign-ups would rise and the KPI would move.

## Pipeline proof

- `stg_back_in_stock_alert_requested`: 6 valid samples pass; 1/1 broken samples caught

**Privacy.** The form collects an email address, but no email, hashed email, name or other contact detail goes into the analytics event or any of its properties. The email goes only to the backend notification/ESP service that sends the alert. The event fires after the backend confirms the alert exists, carrying only product_id, category and price. Make sure the form submit does not put the email in the URL or a query string, because page_viewed.page_path and referrer would then capture it. Use a POST body, not GET parameters. If per-user analysis is needed later, rely on the standard anonymous/user id the SDK already attaches, not the email.
