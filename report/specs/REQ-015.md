# REQ-015: event spec for review

> Track every coupon code entered at checkout, whether it was valid or rejected, and the discount amount when valid.

**Summary.** No catalog event covers coupon entry, so this spec adds one new event, coupon_code_submitted. It fires once each time a shopper submits a code at checkout and the promotion service returns a result. The event records whether the code was valid or rejected, the discount amount when valid, and a structured reason when rejected. To avoid capturing free text the shopper typed, rejected attempts carry no raw input. No existing event changes. No existing KPI's numbers change, because checkout_conversion and store_pickup_adoption read only checkout_started and order_completed, which are untouched. The new event can still be joined to checkout_started via cart_id to segment checkout_conversion by coupon use.

## Questions for the PM
- Do you need the exact text of rejected codes (for example, to spot misspellings of a real code or leaked competitor codes)? The default spec sends only a rejection_reason for rejected attempts, because the coupon field is free text and shoppers sometimes type emails or other personal data into it.
- Can a shopper stack more than one coupon on an order? If so, should discount_amount be the discount from this code alone (the current spec) or the cart's total discount after this code is applied?
- Should coupons applied automatically (from a promo link, or by default) also fire this event, or only codes the shopper types and submits? The spec covers only manual submissions unless you say otherwise.

## Events

| Event | Change | Fires when |
|---|---|---|
| `coupon_code_submitted` | new | Fires once each time the shopper submits a coupon code at checkout (Apply button or Enter) and the promotion/validation service returns a valid or rejected result. Send it from the server-side validation response so status and discount_amount are authoritative. Do not fire on keystrokes or field blur. Fire again on every resubmission, including resubmitting the same code. Do not fire for network or validation errors where no result came back. |

**coupon_code_submitted**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `cart_id` | string | yes | any |
| `status` | string | yes | valid, rejected |
| `coupon_code` | string | no | any |
| `promotion_id` | string | no | any |
| `discount_amount` | number | no | any |
| `cart_value` | number | no | any |
| `rejection_reason` | string | no | not_found, expired, not_started, minimum_not_met, ineligible_items, usage_limit_reached, not_combinable, account_ineligible, other |

## Pipeline proof

- `stg_coupon_code_submitted`: 6 valid samples pass; 4/4 broken samples caught

**Privacy.** The coupon field is free text, and shoppers sometimes paste emails, phone numbers, names or gift-card numbers into it. Never forward the raw input. For rejected attempts send only status and rejection_reason. For valid attempts send the canonical code from the promotion system, not what was typed. Some codes are unique per customer, such as referral codes containing a name or single-use codes emailed to one person. For these, send promotion_id and omit coupon_code, or send a campaign-level code instead. Do not add email, customer name, or any user-entered text as properties. User identity should come only from the standard anonymous/user id handled by the tracking SDK.
