# REQ-019: event spec for review

> Compare products: users pick 2-4 products and see a side-by-side table. Track compares and which products get compared together.

**Summary.** REQ-019 needs one new event, product_comparison_viewed. It fires when the side-by-side compare table is shown with 2-4 products. It records the SKUs being compared so analysts can count compares and build co-comparison pairs and sets. No existing event covers comparing products. product_viewed should not be reused: it would inflate add_to_cart_rate. Whether add-to-cart can happen from the compare table is still open. If it can, product_added_to_cart will need a new source value, which would be an extend; that is not specced until Jon confirms.

## Questions for the PM
- Can users add a product to cart directly from the compare table? If so, I'll extend product_added_to_cart.source with a new allowed value 'compare'. Today those adds would fail validation or be mislabeled as 'pdp'.
- Where can users start a compare: PLP/category grid, search results, PDP, or all of these? If you want compares broken down by entry point, I'll add an optional entry_point property with those values.
- Is the compare table its own page (for example /compare) that fires page_viewed, or an overlay on the current page?

## Events

| Event | Change | Fires when |
|---|---|---|
| `product_comparison_viewed` | new | Fires once when the side-by-side compare table finishes rendering with 2-4 products. Fires again only if the user changes the set of products while on the table (adds, removes or swaps a product). Does not fire on re-renders, scrolls, resizes or toggling table rows. Must not also fire product_viewed for the products in the table. |

**product_comparison_viewed**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `product_ids` | array | yes | any |
| `product_count` | integer | yes | 2, 3, 4 |
| `category` | string | no | any |

## KPIs to confirm before engineering starts

- [ ] **add_to_cart_rate** (owner: growth): The spec adds a new event and does not touch product_viewed or product_added_to_cart, so the KPI should not move. Two cases would change it. First, if engineering fires product_viewed for products shown in the compare table, the views denominator inflates. Second, if users can add to cart from the compare table, those adds are untagged or mis-sourced in product_added_to_cart until a 'compare' source value is added. Growth should confirm the KPI stays scoped to /p/* views.
- [ ] **newsletter_signup_rate** (owner: growth): If the compare table is its own page that fires page_viewed, it can add page views and sessions to this KPI's denominator. That effect is small and only matters if compare becomes a common landing or entry page.

## Pipeline proof

- `stg_product_comparison_viewed`: 6 valid samples pass; 3/3 broken samples caught

**Privacy.** No personal data is needed. Send only SKUs, the product count and the category. Do not put user identifiers, emails or names in the event payload; rely on the standard anonymous or session identifiers your analytics SDK already attaches. If the compare page has a shareable URL, make sure page_path or referrer cannot carry user-entered text or account info in query strings.
