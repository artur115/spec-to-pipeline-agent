# REQ-020: event spec for review

> New checkout is 3 steps: shipping, payment, review. Track each step so we can see where people drop off. Must not break the checkout conversion KPI.

**Summary.** Track the three steps of the new checkout (shipping, payment, review) with two new events: checkout_step_viewed when a step is shown, and checkout_step_completed when the shopper gets past it. Both carry cart_id, so they join to the existing checkout_started and order_completed events and give a funnel: checkout_started → shipping → payment → review → order_completed. checkout_started and order_completed stay as they are. No properties are added, changed or retyped, so the checkout_conversion definition (orders / checkouts started) is untouched. The new checkout must still fire checkout_started exactly once when the shopper enters checkout, before the shipping step. It must fire order_completed exactly once, on the order confirmation, never on the review step.

## Questions for the PM
- Will the new 3-step checkout run alongside the old one (A/B test or gradual rollout)? If so, should we add an optional checkout_version property to checkout_started and order_completed, so checkout_conversion can be split old vs new without changing its definition?
- Is store pickup chosen on the shipping step? If not, which step is it on? The spec assumes the shipping step and records fulfillment_method on checkout_step_completed for that step.
- Do you also need the reason people fail to advance a step (validation error, payment declined)? If yes, we'll spec a separate error event rather than overloading these two.

## Events

| Event | Change | Fires when |
|---|---|---|
| `checkout_started` | reuse | Unchanged: fires once when the shopper enters /checkout, before the shipping step renders. The new checkout must keep exactly this firing point and must not fire it again on step changes, back navigation or page reloads. |
| `checkout_step_viewed` | new | Fires each time a checkout step (shipping, payment or review) is rendered and visible to the shopper. This includes returning to a step via Back or an Edit link. It does not fire again on re-renders within the same visit to that step. |
| `checkout_step_completed` | new | Fires when the shopper successfully moves past a step: validation passed and the app advances. For shipping and payment, this is moving to the next step. For review, it is the Place order submission being accepted for processing, before the confirmation page. It does not fire on failed validation or when going Back. |
| `order_completed` | reuse | Unchanged: fires once when the order is confirmed (order confirmation shown / order created). It must not fire on the review step or on Place order click, and must not fire again if the confirmation page is reloaded. |

**checkout_step_viewed**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `cart_id` | string | yes | any |
| `step` | string | yes | shipping, payment, review |
| `step_number` | integer | yes | 1, 2, 3 |

**checkout_step_completed**

| Property | Type | Required | Allowed values |
|---|---|---|---|
| `cart_id` | string | yes | any |
| `step` | string | yes | shipping, payment, review |
| `step_number` | integer | yes | 1, 2, 3 |
| `fulfillment_method` | string | no | ship, pickup |

## KPIs to confirm before engineering starts

- [ ] **checkout_conversion** (owner: finance-analytics): Its definition and events are not changed, but the new checkout re-implements where checkout_started and order_completed fire. If checkout_started moves (e.g. fires per step or on reload, or only after shipping) or order_completed fires on the review step, the daily ratio shifts. finance-analytics should confirm the firing points before and after launch and compare old vs new flow.
- [ ] **store_pickup_adoption** (owner: retail-ops): Computed from order_completed.fulfillment_method. If the new checkout moves the ship/pickup choice or fails to pass fulfillment_method into order_completed, the pickup share changes. Duplicate order_completed events would also change it.
- [ ] **return_rate** (owner: ops-analytics): Uses order_completed as the denominator. Any change in how often the new checkout fires order_completed (duplicates on reload, missed fires) changes the return rate.

**Privacy.** The shipping and payment steps collect name, email, phone, address and card details. None of these may be sent on the step events. Send only cart_id, step, step_number and the fulfillment_method enum. Do not attach form field values, address strings, postcodes or card BIN/last4. Do not use page URLs that contain query parameters with personal data. If the new checkout puts personal data in the URL, strip it before any page_viewed fires on /checkout. Use cart_id as the join key, never email or phone. If payment method type is wanted later, add it as a fixed enum (e.g. card, paypal), never as card or account details.
